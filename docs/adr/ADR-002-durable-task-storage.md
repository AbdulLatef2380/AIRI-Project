# ADR-002: تخزين المهام الدائمة وسجل العمليات

- **الحالة:** مقبول كهدف معماري؛ التنفيذ والترحيل غير منفذين بعد
- **التاريخ:** 2026-11-21
- **النطاق:** مهام الوكيل، runs/steps، العمليات الخارجية، الأحداث الوصفية، وسجل outbox على Android
- **ترقيم:** هذا هو قرار التخزين في خطة P0. يستخدم ADR-002 لأن `ADR-001-runtime-capability-execution-boundaries.md` موجود مسبقاً في سجل القرارات العام.

## السياق والأدلة الحالية

يخزن `DurableTaskManager` حالياً كيان المهمة المركّب في ملف JSON إصدارّي (`durable_tasks.json`) عبر `DurableTaskFileStore`. الكتابة ذرّية على مستوى الملف الواحد، ويُمنع الاستبدال عند تعذر قراءة المستند أو رفض سجل ملكية؛ لكن حالة المهمة وطلب WorkManager لا يشتركان في معاملة واحدة. كما أن تضمين runs والخطوات والموافقات والأحداث والعمليات الخارجية في مستند مجمّع لا يوفر قيوداً أو CAS/تحديثاً صفياً قابلاً للمعاملة بين هذه السجلات.

توجد `AiriDatabase` كقاعدة Room الأساسية (`airi_memory_db`)، إصدارها 11، ولها migrations متسلسلة من 1 إلى 11 ومخططات Room المصدرة. وهي المرشح الأساسي لتخزين المهمة والمعاملة في Android. قاعدة `AgentRunDatabase` منفصلة ومخصصة لسجل التشغيل/التاريخ؛ لا تُعتمد مصدراً لحالة المهمة أو outbox.

لا تتضمن نسخة المستودع عينة من `durable_tasks.json` لمستخدم فعلي، ولا تتوفر قياسات إنتاجية لحجم الملف أو عدد المهام/الأحداث أو كلفة ترحيلها. لذلك لا يثبت هذا القرار أن الأداء أو المساحة قد قيسا على بيانات مستخدم، ولا يجيز حذف ملف JSON أو الكتابة فوقه.

## القرار

1. على Android، تكون قاعدة SQLite التي تديرها `AiriDatabase` المصدر المعاملي لحالة المهمة وسجلات `run`, `step`, `tool/external operation`, وبيانات الأحداث اللازمة للمصالحة، إضافة إلى outbox لأوامر الجدولة. توضع كل السجلات التي يجب أن تتغير معاً في قاعدة SQLite نفسها، وتُحدّث ضمن معاملة واحدة.
2. تُعرّف واجهة تخزين محايدة عن Android (مثل `TaskStore`) كي لا تعتمد نماذج المجال على Room. لا تستخدم `AgentRunDatabase` كمخزن بديل لحالة المهمة.
3. لا تدخل WorkManager أو أي API مزود خارجي في ادعاء المعاملة. بعد commit للـoutbox، يعالج reconciler الأوامر بإرسال idempotent/unique work؛ وعند التعطل يعيد اكتشافها ومصالحتها.
4. تبقى الملفات/النتائج الكبيرة خارج SQLite كـartifacts بمراجع وhashes. لا تحفظ مفاتيح أو secrets أو payloads حساسة غير منقحة في سجل الأحداث.
5. يبقى JSON الحالي صيغة ترحيل/استيراد وتصدير ووسيلة استعادة أثناء الانتقال. لا يُحذف ولا يُستبدل ولا يتوقف استعماله قبل اجتياز بوابات الترحيل أدناه. لا تعتمد كتابة مزدوجة مستمرة كحالة نهائية.
6. يستخدم Desktop عقد المجال نفسه مع تنفيذ SQLite مناسب للمنصة؛ لا يفرض Android Room على Desktop.

## بوابات الترحيل والتراجع

لا يبدأ cutover إنتاجي حتى تتحقق جميع الشروط التالية:

- جرد موثق لموضع JSON الفعلي وحالات missing/empty/invalid، وعدد السجلات، وحجم الملف ونسخته، بعد أخذ موافقة/إتاحة القياس من دون تسجيل محتوى حساس. تُحفظ نتائج القياس كبيانات إجمالية فقط.
- ترحيل قابل لإعادة التشغيل، idempotent، داخل معاملة قاعدة بيانات، مع حفظ بصمة ملف المصدر وإصدار المخطط وعلامة اكتمال الاستيراد. تُرفض الملفات المعيبة أو ذات الملكية غير الصالحة fail-closed؛ لا تتحول إلى قائمة فارغة ولا يُسمح لعملية ترحيل أن تكتب فوق المصدر.
- مقارنة عدد/هويات السجلات والروابط والقيود بعد الاستيراد، ثم تحقق round-trip/قراءة عينة منظمة من كل الأنواع المدعومة. لا تُحذف نسخة JSON الأصلية بعد نجاح الاستيراد الأولي.
- اختبارات migrations من قاعدة قديمة فعلية/fixture ممثلة، واختبار تراجع يثبت أن فشل migration أو الاستيراد يترك قاعدة البيانات السابقة وملف JSON قابلين للقراءة دون فقد أو استبدال. تختبر أيضاً إعادة التشغيل بعد crash عند كل حد commit/import.
- تحقق backup/restore لقاعدة Room الجديدة، وسياسة الاحتفاظ بنسخة JSON حتى اكتمال إصدار مستقر ودورة تحقق لاحقة. يجب أن يكون rollback قبل أول كتابة متباينة إلى مصدرين؛ بعد cutover، تكون الاستعادة من النسخة المعتمدة وإعادة الاستيراد وفق إجراء موثق، لا الرجوع الصامت إلى JSON قديم.
- بوابة بناء واختبارات Android/Room على بيئة فيها Android SDK. اختبارات JVM المنتقاة لا تثبت Room migrations أو تكامل WorkManager.

إلى أن تُستوفى هذه الشروط، يبقى التنفيذ الحالي هو المصدر العامل ولا تُجرى إزالة أو إعادة تسمية لـ`durable_tasks.json` أو مسار fallback له.

## العواقب والقيود

- يتطلب القرار إضافة كيانات وDAOs وmigration تالٍ لـ`AiriDatabase`، ثم استبدال واجهة التخزين خلف `DurableTaskManager` تدريجياً، مع تغطية SQLite للمعاملة وCAS. هذا العمل لم يُنفذ بمجرد اعتماد ADR.
- يجب التحقق من مساحة/أحجام سجلات المهمة الفعلية قبل اختيار حدود الاحتفاظ والتقسيم؛ الحد الحالي للأحداث داخل نموذج المهمة لا يغني عن قياس حجم التخزين.
- تبقى ملفات JSON القديمة متاحة للاسترداد خلال الانتقال، لكن وجودها لا يعني أن النظام سيكتب إليها بعد إتمام cutover.
- أي خلل في التكامل أو القياس يعيد فتح هذا القرار قبل cutover بدلاً من إسقاط بوابات سلامة البيانات.
